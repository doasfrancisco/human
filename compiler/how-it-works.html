How human works

One project, three actors, one folder. Every flow below is one thing you can ask for, from the line you type to the file the tool writes.

The pieces

Nine files do the work. Three run as the tool, three are instructions claude reads, one is the shape catalog, two draw.

tool
compiler/cli/human/__init__.py
The door. Reads what you typed and hands it on: init, serve, skills, map, retext, undo, show, lines, sync, train.
tool
compiler/cli/human/decompiler.py
Every shared rule: what a block is, what a pin is, the gates, and the commands show, retext, undo, sync. Holds the two letters to claude.
tool
compiler/cli/human/cmd_map.py
Saves one entry: numbers it, checks its pins, ties it to its exact lines.
tool
compiler/cli/human/cmd_train.py
A training session: opens it, keeps three versions per row, applies the pick, closes it.
tool
compiler/cli/human/cmd_store.py
The training store: the login with a key, and the four calls to the Lambda that keeps the sessions in S3.
claude reads
skills/decompile/SKILL.md
How to explain code that exists: the reader, the shape, the pins, the map, the sync.
claude reads
skills/human/SKILL.md
How to compile an abstraction into code, then map the code's telling and your own words on top.
claude reads
skills/shapes/SKILL.md
The only door into the shape catalog: how a shape enters or changes.
catalog
shapes/*.md
rail, sections, desk, dialogue, skeleton. One file per shape: when it fits, the rules, one example.
reader
reader/web.html · trees.js · feed.html
The page that draws the abstractions, the file tree, and the swipe feed of a training session.

The state

Everything the project writes lives in one folder. Remove it and nothing else changes.

project/ ├── abstraction.txt your words, verbatim — the source the verbatim gate measures against ├── src/app.py the code └── human/ ├── human.json the top: one entry with a pin per file, plus the file list and the ignore list ├── explanation_src__app.py.json the map of one file: its entries, one per abstraction ├── web.html · trees.js · feed.html the reader, copied in by init └── project.json the tellings of the whole project the training sessions are not on disk: they live in the training store, an S3 bucket behind a Lambda, one JSON per session under your user id

One map, read from the top down

your words
entry 2 — the abstraction, verbatim, with pins [hello world](e1:the answer) into entry 1
holds no line numbers of its own — it inherits them through the chain
↓ e1: pin
the detailed telling
entry 1 — the whole file in a shape from the catalog, with pins [the answerer](Hello) into the blocks
a zoom on one block is one more entry, with --block
↓ block pin
the code
block Hello → lines 12–31
a block is a function or a class of a python file, a heading of a markdown file, a once-only tag or a named function of a web page
explanationone entry of a map
→
anchorthe words in brackets
→
blocka real piece of the file
→
linesresolved by the tool, never typed

A pin never crosses a file border at the e<id>: level. A pin to another file — [the map command](src/cmd_map.py) or [one piece](src/cmd_map.py:parse_target) — is the only bridge between two maps. The pins of human.json are those bridges only.

Flow 1 · decompile — the code exists, the words come after

You point at a file. Claude writes the telling. Nothing touches the map until you say the word.

you
ask for a file
/decompile src/app.py
claude
reads the file and picks the shape from the kind of file
one run → rail · a set of functions → sections · a dispatcher → desk · a rulebook → dialogue
claude
writes the telling for a reader who does not read code
pins on the words that name a thing: [the start](main). Every other word is free; the layout carries no meaning.
claude
shows the text and stops
even when your message sounded like approval in advance
you
say the word
"map it" — or paste a line you want reworded, and the loop goes back one step
claude
pipes the exact text into the tool
human map src/app.py <<'EOF' … EOF
tool
gates the entry, no claude call
every pin points at a real block, a real earlier anchor, or a real file?
no two pins share the same words?
no circle through the e<id>: pins?
a verbatim text matches abstraction.txt character for character?
a refusal is the gate speaking: claude reads it, fixes the text, runs again
disk
one entry appended, never one changed
human/explanation_src__app.py.json — the id, the block, the text, every anchor with its lines, the coverage
claude
reports
the entry, its anchors, the coverage, the warnings of human show, and offers the next telling — a zoom on one block, or a plainer layer over the whole

Flow 2 · compile — your words come first, the code after

The human language. You write the abstraction; claude writes code under it and ties both to the same lines.

you
give an abstraction
/human an http server using python that returns hello world
claude
keeps your words
writes them verbatim into abstraction.txt — no spelling fixed, no word trimmed
claude
writes the code files, no comments
the gate is static like a compiler's: the file must parse. No run, no test.
tool
registers the project
human init
scans the tree through the ignore sieve, writes the file list into human.json, copies the reader in
claude
maps the detailed telling of each file
entry 1, in a shape from the catalog, pins into the blocks
claude
maps your words on top
human map src/app.py --verbatim abstraction.txt
pins inserted — [hello world](e1:the answer) — the rest untouched
tool
the verbatim gate
strips the pins out and compares the rest against abstraction.txt. A changed word is a refusal. Pins go in; your words never change.
claude
reports and serves
human show per file, then the reader address

Afterwards you correct in the reader and with retext, undo, sync — the same commands as flow 1. Both flows end in the same folder with the same shape of map; only the order of words and code differs.

Flow 3 · read

you
start the reader from anywhere in the project
human serve
tool
climbs to the folder that holds human/human.json and serves it
prints the localhost line and the tailnet line; takes the next port when 8010 is busy
tool
answers human.json with a live file list
a fresh disk sweep through the ignore sieve on every ask — a deleted file leaves the tree, a new one appears, no init, no restart
you
open the page
http://localhost:8010/human/web.html
human.json opens first — the top of the project, one pin per file
a file shows every entry as one folded header: the most detailed first, the one nothing points at last
a click on a pin jumps to its entry; a pin with no entry behind it shows muted
a cross-file pin switches file; a file with no map shows its raw lines

Flow 4 · sync — the code changed

The maps follow the code. One command, exactly once per change.

you
change the code, then
human sync src/app.py
the old version is git HEAD; --old <file> when it lives elsewhere
tool
a deterministic pass, no claude
maps every old line to its new line; re-resolves every block pin and every entry span. Lines that only moved end here.
tool
finds the entries the change touches
an entry whose lines changed, an entry with a broken pin, an entry whose block gained new lines
tool
writes the letter to claude
the file, its absolute path — read the whole file the unified diff the project files the file imports: all — added — removed the blocks of the new file, the entries that need mending the rules: keep every untouched line verbatim, keep every anchor, retarget a renamed block, add a sentence for each behaviour the change added
claude
answers with the mended texts, run at the project root
reads the file, and the imported project files when a new sentence needs them — never the rest of the project
tool
gates the answer on a copy, up to --tries times
every block still exists?
every anchor kept?
every text rebuilt cleanly?
a gate that fails sends the letter again with the refusal; four failures leave the map untouched
disk
the map saved; the entries that point into a mended one marked stale
a warning when new lines landed inside an entry and no word changed: those lines got no sentence

human sync . at the root re-resolves the pins of human.json against the project, no claude call. A pin whose file is gone is reported; you repair it with retext.

Flow 5 · carry down — a parent telling changed

The layers of one map stay true one layer at a time, downward only, on your word — never recursively in one breath.

disk
entry 1 changed
by a sync, or by a retext — and entry 2 points into it, so entry 2 is marked stale with a copy of the old text
you
ask for the repair
human sync src/app.py --stale 2
tool
writes the second letter
the old text of the parent, the new text, the diff between the two the dependent's text the rules: mend the words that went wrong, keep every anchor, carry a new fact down at the dependent's own level — a plainer layer says less, never nothing — pinned at the parent's new anchor
claude
answers with the mended dependent — words only, never code
tool
gates and saves; the dependents of entry 2 are marked stale in turn
a parent's child can be a parent — the next layer waits for your next word

Flow 6 · train — the catalog learns from real picks

you
open a session
human train --open
rows without a pick from the last session carry over
claude
on the next /decompile or sync, writes three versions per file instead of one
best — the catalog shape for this kind of file, --shape name
refinement — for a sync row, the map's own text, filled by the tool
free — no shape rule, anything that explains
human train src/app.py --kind sync --entry 1 --as best --shape sections <<'EOF' … EOF
every version passes the same pin gates as a map; a rewrite keeps its earlier text in the history — v1, v2, v3
tool
serves the feed
http://localhost:8010/human/feed.html
the session list and the fresh map come as JSON; a pick lands in the open session over POST, no restart
you
swipe and pick
sideways for the versions, down for the next file, a comment if you want: "the start explains better how the prompt worked."
you
close
human train --close
tool
applies each pick as a retext of the entry, then marks the session finished
a row without a pick carries over; the maps never change before the close
disk
the training store · sessions/<user>/<session>.json in S3, through the Lambda, with the key of human login
the rows, the three versions with their shape tag and history, the pick, the comment, a copy of the code and of the text before — the record the shapes flow reads

Flow 7 · shapes — how the catalog changes

claude
reads the finished sessions
which slot won, which shape it wore, what the comment said; feedback/sessions.json remembers which sessions were read
claude
tells you what it learned, and the fix it would make
"a line is short because it drops the fields, never because it drops the behaviour"
you
validate — or not
a shape enters or changes only on a real instance you validated; the shapes skill is the only door into the folder
claude
edits shapes/<shape>.md, bumps the version, reinstalls, redeploys with human skills
the next /decompile reads the new rule

The project level today

What exists above one file, as it stands. The place a whole-project abstraction would have to fit.

human.jsonone entry: one line per file, each a file pin — "what the file does"
→
file pin[the door](src/__init__.py) leads to that file's whole-file entry
→
file:block pin[one piece](src/cmd_map.py:parse_target) leads to one block's entry, muted when none
holds
The file list and the ignore list, swept fresh on every serve. One entry, made with human map ., whose pins are file and file:block pins only.
does not hold
A telling of a run that crosses files — "you type a command, the door reads it, the tool checks the pins, the map is written" — with layers of its own. No e<id>: pin lives in human.json, and no e<id>: pin crosses a file border.
keeps true by
human sync . re-resolving the file pins; nothing carries a fact from one file's map into another's — a sentence lives in one file's map only, and every other map points at it.
